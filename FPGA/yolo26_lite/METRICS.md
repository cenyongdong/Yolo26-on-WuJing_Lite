# 性能计数与验收

`software/include/yolo26/metrics.hpp` 定义所有计数口径。采集、预处理、推理、尾处理、合成和显示采用
分别提交完成事件；每个事件包含启动代次、帧号、采集／阶段开始／完成的单调时钟时间。
每阶段只有一个按序完成的执行者。错误代次、重复／倒序帧和非法时间只增加隔离计数。
采集与推理线程可并发更新不同阶段，统计器内部互斥；事件路径只访问预分配内存，不写磁盘。

## 严格 30FPS

- 测量范围为 `[start, start + seconds)`，预热和结束边界外事件不计 FPS。
- 各阶段按实际完成时间分配到连续、互不重叠的 1 秒窗口；空窗口必须保留为 0。
- 所有计划秒完成且每个推理窗口均至少 30 个不同有效帧，才设置逐秒吞吐通过。
- `camera_30fps_10min_passed` 还要求实时摄像头来源和至少 600 秒完整测量。
  文件回放和合成来源即使计算吞吐足够，也不能设置这个字段。
- 中途停止按实际已观察时长计算均值，但完整测量标志为 false，不能用截短测量宣称通过。
- HDMI 刷新增量单独记录，不增加显示采用／推理帧数；SDK 返回之前、非法输出和重复画面不能提交推理完成。

统计器只能核验事件身份、时间和计数，不能替代实际 SDK 完成、摄像头来源及无效结果隔离的证据。
管线必须在真实有效输出完成时调用它，最终同时保存原生执行结果、设备身份和软件／模型身份。

## 矩形文件序列

预先加载不同 RGB 帧，整组预热后开始计时并循环播放，每次重新调用 SDK 和尾处理。
逐秒统计整个推理调用，预热原值先驻留在内存，关闭 SDK 后再完整落盘。计时中轮流抽查，
结束后再对每份输入比较完整张量。实际完成时间过截止线的调用排空后记入窗外。
最慢 16 次且达到 40ms 的调用留存各段时长、线程 CPU 时间、缺页和上下文切换次数。
重复的是输入序列，每次执行有独立帧号；完成回执的来源保持 `file_sequence`。

## 延迟与资源

每阶段报告执行时长及采集到完成的 P50/P95/P99/最大值，采用 nearest-rank 纳秒整数。
最大间隔包含测量开始到首帧、相邻帧、末帧到结束三个范围，零帧阶段也会报告完整空白时长。
每阶段最多保存 `seconds × 120` 份延迟样本；超量仍准确计帧，但分位数置空并报告遗漏数，避免偏采样冒充完整统计。
最长测量 3600 秒，构造时分配窗口与样本容量，执行过程中不扩容。

分别记录满池、最新项替换、非法结果、设备错误、日志队列满等原因，以及原始／输入／显示池高水位。
默认池上限为 6／3／3，观察到超限视为调用错误。`finalize` 应在各生产者停止提交后调用，随后拒绝新事件。
`write_metrics_json` 在视频停止后或独立记录线程写入报告，保持 JSON 的十进制和 locale 独立性。

## 已验证范围

2026-11-14：六个本机 CTest 通过。统计测试使用合成事件，覆盖完整 600 秒轨迹、
相邻秒 59/1 而均值仍为 30 的拒绝案例、回放来源、测量边界、去重、旧代次、非法时间、
提前结束、延迟容量超限及并发阶段更新。合成事件测试不证明硬件达到 30FPS。
