### 转置收益为何被抵消

| 共同区域组成 | 原共享 ms | 4×4→8×8 ms | 5×5→10×10 ms |
|---|---:|---:|---:|
| Transpose | 7.401 | 4.930 | 5.652 |
| Copy | 1.740 | 0.142 | 0.142 |
| #3240 核心 | 1.898 | 1.976 | 1.897 |
| #3295 核心 | 1.143 | 3.455 | 2.499 |
| #3296 核心 | 1.734 | 1.741 | 2.435 |
| Upsample | 1.318 | 1.472 | 1.660 |
| Concat | 0 | 3.184 | 2.654 |
| 合计 | **15.235** | **16.900** | **16.941** |

4×4 方案的转置＋Copy 减少 **4.070ms**，但新 Concat 增加 3.184ms、#3295 核心增加 2.312ms；
计入另外两个核心和上采样变化后，区域净增 **1.665ms**，提交＋等待净增 1.666ms。
5×5 的转置＋Copy 减少 **3.346ms**，新 Concat 增加 2.654ms、#3295 增加 1.356ms，
还伴随 #3296 增加 0.701ms、上采样增加 0.342ms，区域净增 **1.706ms**。
逐层计时与普通墙钟来自不同帧组；这些结果支持区域退化的归因，不应相减制造精确 SDK 开销分解。

共同区域的静态指令读写请求仍从 129.086MiB 降至 117.560／121.064MiB，实际时间却变长。
两图各减少 25MiB 转置和 12.5MiB Copy 请求，同时新增 25MiB Concat；核心请求也有变化。
这证明本次生成路径不能用总请求字节量单独预测性能，不否认其它直接写入或分支存储方案。

### 已有指令证据与尚未测量的原因

| #3295 核心 | 原共享 | 4×4 | 5×5 |
|---|---:|---:|---:|
| 内部 batch × 块高 × 块宽 | 16×10×10 | 100×4×4 | 64×5×5 |
| 输入唯一地址量 MiB | 3.125 | 3.125 | 3.125 |
| 输入读取请求 MiB | 3.125 | 7.227 | 7.227 |
| 输入请求／唯一地址量 | 1 | 2.3125 | 2.3125 |
| 权重读取请求 MiB | 4.000 | 3.000 | 3.000 |
| 最终展开 RXLM／RKLM 指令数，各自 | 32768 | 204800 | 131072 |

算术问题和权重没有变，但小块使内部 batch 及指令数增多；4×4、5×5 的 RXLM／RKLM 分别增至 6.25／4 倍。
**已证明的是请求与生成调度变化，以及核心实际变慢；未测量的是物理 DDR 停顿和各计算通道利用率。**
两候选 #3295 的外存请求相同却耗时不同，也说明不能把全部核心差值都归因于输入重读。
更短空间块导致并行资源利用不足、指令与流水开销增多是待验证解释，不能从这些数值反推准确利用率。

#3296 的输入请求比在三图中始终为 1，权重请求却为 2.633／0.500／4.000MiB，
RXLM 数为 16384／102400／65536。4×4 的请求更少而核心时间几乎不变，5×5 核心变慢，
进一步表明输入复用、权重调度、空间几何和转换须同时比较。

公开读写 Tile 计数全部为 0，本轮不据此计算带宽或声称没有 DDR 访问。

优化顺序：优先分析慢 1×1 卷积的输入／部分和 Tile 复用和等价矩阵映射；Split/Concat 的
保守复制削减已完成有限板测，结果见下文。仅删除本批 Copy＋Transpose 的直接执行时间最多约 8ms，
但布局改变若改善后续卷积复用，收益可能超出这个直接时间，不能据此排除布局优化。
本批是固定输入短测，不是相机 30FPS、长期实时性或 mAP 验收。

- `npu-deployment.json`：公开 runtime value／planning value 元数据、存储位置、分段、别名、

也在已计时区间外。它们仍可能影响下一帧的缓存状态，因此普通样本与附加诊断样本分开汇总。

## 解释要求

映射使用实际融合成员顺序与生成图 layer_count；零层 Reshape/Split 等不占计时槽。
原生数组的长度、有限性、层时间是否累积及与总计时关系必须核验。只读到一个数组不算完成归因。
Tile 计数不等于流量；SDK 时钟参数不等于已测频率；显存节约不等于带宽降低。
三种策略使用相同模型、输入、二进制、BOOT 与 SDK，每批在新的启动代次单独完成及关闭。

## 离线分析

`tools/analyze_npu.py --graph <固定ZG图> --run <回传目录> --output <新JSON>` 默认保留
`unverified` 计时解释，只报告原数组的和、末项、calcTime 及普通调用统计，不生成算子排名。
核验硬件语义后显式选择 `--timer-semantics durations` 或 `cumulative`；多个 `--run`
构成同模型／输入／ELF／SDK／BOOT 的跨启动比较。前三次预热及末尾诊断样本不进入普通稳态汇总。
输出完整逐算子排名和类别合计，不把低样本数的 P99 当作长期实时保证。

六项独立单元测试覆盖融合顺序、零层、多层、缺失/重复成员、计时语义、非有限值、别名、
对照身份及原始计时换算。原始计时使用独立固定计数小例核验，不拟合比例。
默认模式会明确保留异常计时状态，同时仍可比较独立墙钟结果；显式层归因模式拒绝异常样本。
利用已有真实初始化记录，静态映射覆盖全部 399 个原始 HardOp、322 个计时槽和 77 个零层节点；
这项静态映射验证本身没有产生新的硬件计时；实际结果见本页上方。

2026-11-14 只读核查板端 `libicraft_xrt.so` 的公开 `getLayerTime(int)` 与 `calcTime()` 实现：
前者读取 `layer_count × 4` 个字节，按 uint32 累计计数及 256 Icore 周期量子换算，再作相邻差；
返回值是层间隔。离线工具从公开 MemChunk 保存的原始字节重新计算，并检查 API 对应及单调性。
该规则仅适用于已核对的库 SHA256 `a29e4eee6106afae0b6aada4a07e85416ac6dfc3e74083033ae5d1411749dc96`。
公开函数只读检查保存在 `.local/yolo26-ocm-build-r1/inspect-sdk.stdout`；它没有初始化 SDK 或启动 NPU。
软件换算核验不能代替实际时钟测量，仍须比较层时间和、原生总计时与调用墙钟。

## 存储与卷积循环分析

### 最终指令中的输入复用

追加 `dump_instlogs = true` 导出原厂最终指令；生成 JSON 与 RAW 均和已板测基线逐字节相同，

日志哈希、地址区间并集、请求量和计算量。工具 `tools/analyze_instructions.py` 只读最终 Instructions
区段，跳过 TaskGen 和 WETM 状态触发，拒绝未知寻址模式；三项独立手算测试通过。

|---|---|---:|---:|---:|---:|---:|
| 3296 | 1×1 | 19.040 | 12.5 | 194.141 | 15.531 | 16.18 |
| 3240 | 1×1 | 18.794 | 6.25 | 187.891 | 30.063 | 16.44 |
| 3223 | 1×1 | 15.192 | 12.5 | 153.125 | 12.250 | 19.31 |

前三层权重读取请求各自只覆盖一次唯一权重区域，输出也只写一次；没有在这些层的最终 ETM
指令中看到额外外存部分和读写槽。编译计划更明显的代价是 K 时间分块间的输入重读，不能把
所有 C 累加都想象成 DDR 往返。3×3 多次 MAC 使用片上输入／权重，静态请求算术强度高得多。

这是比循环边界更直接的代码生成证据，但仍不是 DDR 总线计量：运行时地址映射／优化、OCM、
突发、总线协议和重叠执行均可能影响物理事务及时间。三层大输入在本次 OCM 放置中均为 DDR。
优先尝试在更小空间 Tile 上容纳更多 K 通道的部分和，使输入跨 K 复用；需要同时核对
YLM 容量、权重加载、并行度和流水重叠。等价 Matmul 是另一条候选路径，不预设一定更快。

循环日志还给出一条可用原厂生成器验证的路线：当前 80×80／40×40 大空间 1×1 的
`kt_MPU_t=1`，20×20 的若干 1×1 已选 `kt_MPU_t=4/5`，后者在片上复用输入计算多个 K 块。
可隔离测试将大空间的独立像素重排成多个小空间块／内部 batch，再作同权重 1×1 并还原；
外部输入仍为 batch=1、640×640，不改变逐像素数学。该路线尚未改图或验收，需计入 packed
布局重排及拼接成本，并验证新的累加划分是否改变 FP16 输出；不能据小图速度直接外推整图收益。
